## Структура скилла

Каждый скилл — это директория в `skills/` с единственным файлом `SKILL.md`:

```
skills/
└── название-скилла/
    └── SKILL.md
```

### Формат SKILL.md

Файл состоит из двух частей: фронтматтер (YAML) и тело (Markdown).

```markdown
---
name: название-скилла
description: Одна строка — что делает скилл и когда его применять.
when_to_use: конкретное условие при котором Roo должен загрузить этот скилл
version: 1.0.0
languages: all
---

# Заголовок скилла

## Обзор

Краткое описание проблемы которую решает скилл и основного принципа.

## Железный закон

Самое важное правило — то что нельзя нарушать.

## Когда использовать

Конкретные ситуации.

## Рабочий процесс

Пошаговые инструкции.

## Красные флаги

Признаки того что что-то идёт не так.
```

### Обязательные поля фронтматтера

| Поле | Описание |
|------|----------|
| `name` | Уникальное имя, совпадает с именем директории. Только строчные буквы и дефисы. |
| `description` | Одна строка. Используется Roo для автоматического выбора скилла. |
| `when_to_use` | Условие загрузки. Чем конкретнее — тем лучше. |
| `version` | Семантическое версионирование: `MAJOR.MINOR.PATCH` |
| `languages` | `all` или конкретные языки через запятую: `typescript, python` |

## Как добавить новый скилл

### 1. Убедись что скилл нужен

Хороший скилл:
- Решает конкретную повторяющуюся задачу
- Содержит проверенный рабочий процесс, а не просто советы
- Имеет чёткое условие применения — Roo должен понимать когда его загружать
- Не дублирует существующие скиллы

Плохой скилл:
- Слишком общий ("пиши хороший код")
- Дублирует то что Roo умеет без скилла
- Не имеет конкретного рабочего процесса

### 2. Создай директорию и файл

```bash
mkdir skills/название-скилла
touch skills/название-скилла/SKILL.md
```

### 3. Напиши скилл

Следуй формату описанному выше. Ориентируйся на существующие скиллы — например [`skills/tdd/SKILL.md`](skills/tdd/SKILL.md) или [`skills/systematic-debugging/SKILL.md`](skills/systematic-debugging/SKILL.md).

**Принципы хорошего скилла:**

- **Конкретность.** "Запусти `npm test путь/к/тесту.test.ts` и убедись что тест падает" лучше чем "запусти тесты".
- **Железный закон.** Одно главное правило которое нельзя нарушать — выдели его явно.
- **Красные флаги.** Список признаков что разработчик отклоняется от процесса.
- **Примеры.** Конкретный код лучше абстрактных описаний.
- **Без воды.** Каждое предложение должно быть полезным.

### 4. Протестируй локально

```bash
# Установи скилл
./install.sh

# Перезагрузи VS Code и проверь что Roo видит скилл
# Попроси Roo: "Используй скилл название-скилла"
```

### 5. Добавь скилл в README

Добавь строку в соответствующую таблицу в [`README.md`](README.md):

```markdown
| [`название-скилла`](skills/название-скилла/SKILL.md) | Краткое описание | Когда использовать |
```

## Как улучшить существующий скилл

1. Найди файл скилла в `skills/название-скилла/SKILL.md`
2. Внеси изменения
3. Увеличь версию в фронтматтере:
   - Исправление опечатки или уточнение → `PATCH` (`1.0.0` → `1.0.1`)
   - Новый раздел или улучшение процесса → `MINOR` (`1.0.0` → `1.1.0`)
   - Кардинальное переосмысление скилла → `MAJOR` (`1.0.0` → `2.0.0`)

## Стандарты качества

### Язык

Все скиллы пишутся на **русском языке**. Это принципиальное решение проекта — скиллы должны быть понятны русскоязычным разработчикам без языкового барьера.

Исключение: примеры кода — на языке программирования задачи.

### Тон

- Прямой и конкретный. Без воды и корпоративного языка.
- Императивный: "Запусти тест", "Проверь", "Убедись" — не "Рекомендуется запустить".
- Без снисхождения, но и без излишней строгости.

### Длина

Скилл должен быть настолько длинным насколько нужно — и ни строчкой длиннее. Если скилл занимает больше 400 строк — скорее всего его стоит разбить на два.

## Процесс отправки PR

1. Форкни репозиторий
2. Создай ветку: `git checkout -b feat/название-скилла` или `fix/название-скилла`
3. Внеси изменения
4. Убедись что `./install.sh --dry-run` отрабатывает без ошибок
5. Создай PR с описанием:
   - Что добавляет/меняет скилл
   - Почему это полезно
   - Как тестировал

### Шаблон описания PR

```
## Что делает этот PR

Добавляет скилл `название-скилла` для [описание задачи].

## Почему это полезно

[Объяснение проблемы которую решает скилл]

## Как тестировал

- Установил через `./install.sh`
- Попросил Roo использовать скилл для [конкретная задача]
- Убедился что Roo следует процессу описанному в скилле
