# Антипаттерны тестирования

## Обзор

Тесты должны верифицировать реальное поведение, а не поведение моков. Моки — это средство изоляции, а не то что тестируется.

**Основной принцип:** Тестируй что делает код, а не что делают моки.

**Строгое следование TDD предотвращает эти антипаттерны.**

## Железные законы

```
1. НИКОГДА не тестируй поведение моков
2. НИКОГДА не добавляй методы только для тестов в продакшн-классы
3. НИКОГДА не мокируй без понимания зависимостей
```

## Антипаттерн 1: Тестирование поведения моков

**Нарушение:**
```typescript
// ❌ ПЛОХО: Тестируем что мок существует
test('рендерит боковую панель', () => {
  render(<Page />);
  expect(screen.getByTestId('sidebar-mock')).toBeInTheDocument();
});
```

**Почему это неправильно:**
- Ты верифицируешь что мок работает, а не что компонент работает
- Тест проходит когда мок присутствует, падает когда его нет
- Ничего не говорит о реальном поведении

**Исправление:**
```typescript
// ✅ ХОРОШО: Тестируем реальный компонент или не мокируем его
test('рендерит боковую панель', () => {
  render(<Page />);  // Не мокируем боковую панель
  expect(screen.getByRole('navigation')).toBeInTheDocument();
});
```

### Функция-ворота

```
ПЕРЕД утверждением на любом элементе мока:
  Спроси: "Я тестирую реальное поведение компонента или просто существование мока?"

  ЕСЛИ тестирую существование мока:
    СТОП — Удали утверждение или убери мок компонента

  Тестируй реальное поведение вместо этого
```

## Антипаттерн 2: Методы только для тестов в продакшне

**Нарушение:**
```typescript
// ❌ ПЛОХО: destroy() используется только в тестах
class Session {
  async destroy() {  // Выглядит как продакшн API!
    await this._workspaceManager?.destroyWorkspace(this.id);
    // ... очистка
  }
}

// В тестах
afterEach(() => session.destroy());
```

**Почему это неправильно:**
- Продакшн-класс загрязнён кодом только для тестов
- Опасно если случайно вызвать в продакшне
- Нарушает YAGNI и разделение ответственности

**Исправление:**
```typescript
// ✅ ХОРОШО: Утилиты тестов обрабатывают очистку тестов
// Session не имеет destroy() — он без состояния в продакшне

// В test-utils/
export async function cleanupSession(session: Session) {
  const workspace = session.getWorkspaceInfo();
  if (workspace) {
    await workspaceManager.destroyWorkspace(workspace.id);
  }
}

// В тестах
afterEach(() => cleanupSession(session));
```

### Функция-ворота

```
ПЕРЕД добавлением любого метода в продакшн-класс:
  Спроси: "Это используется только тестами?"

  ЕСЛИ да:
    СТОП — Не добавляй
    Помести в утилиты тестов вместо этого

  Спроси: "Этот класс владеет жизненным циклом этого ресурса?"

  ЕСЛИ нет:
    СТОП — Неправильный класс для этого метода
```

## Антипаттерн 3: Мокирование без понимания

**Нарушение:**
```typescript
// ❌ ПЛОХО: Мок ломает логику теста
test('обнаруживает дублирующийся сервер', () => {
  // Мок предотвращает запись конфига от которой зависит тест!
  vi.mock('ToolCatalog', () => ({
    discoverAndCacheTools: vi.fn().mockResolvedValue(undefined)
  }));

  await addServer(config);
  await addServer(config);  // Должен бросить — но не бросит!
});
```

**Почему это неправильно:**
- Замоканный метод имел побочный эффект от которого зависел тест (запись конфига)
- Чрезмерное мокирование "для безопасности" ломает реальное поведение

**Исправление:**
```typescript
// ✅ ХОРОШО: Мокируем на правильном уровне
test('обнаруживает дублирующийся сервер', () => {
  // Мокируем медленную часть, сохраняем поведение нужное тесту
  vi.mock('MCPServerManager'); // Просто мокируем медленный запуск сервера

  await addServer(config);  // Конфиг записан
  await addServer(config);  // Дубликат обнаружен ✓
});
```

### Функция-ворота

```
ПЕРЕД мокированием любого метода:
  СТОП — Не мокируй пока

  1. Спроси: "Какие побочные эффекты имеет реальный метод?"
  2. Спроси: "Зависит ли этот тест от любого из этих побочных эффектов?"
  3. Спроси: "Полностью ли я понимаю что нужно этому тесту?"

  ЕСЛИ зависит от побочных эффектов:
    Мокируй на более низком уровне (фактическую медленную/внешнюю операцию)
    ИЛИ используй тестовые дублёры сохраняющие необходимое поведение
    НЕ высокоуровневый метод от которого зависит тест

  ЕСЛИ не уверен что нужно тесту:
    Сначала запусти тест с реальной реализацией
    Наблюдай что реально нужно происходить
    ЗАТЕМ добавь минимальное мокирование на правильном уровне
```

## Антипаттерн 4: Неполные моки

**Нарушение:**
```typescript
// ❌ ПЛОХО: Частичный мок — только поля которые ты думаешь нужны
const mockResponse = {
  status: 'success',
  data: { userId: '123', name: 'Алиса' }
  // Отсутствует: metadata которую использует нижестоящий код
};
```

**Почему это неправильно:**
- Частичные моки скрывают структурные допущения
- Нижестоящий код может зависеть от полей которые ты не включил
- Тесты проходят но интеграция падает

**Исправление:**
```typescript
// ✅ ХОРОШО: Отражаем полноту реального API
const mockResponse = {
  status: 'success',
  data: { userId: '123', name: 'Алиса' },
  metadata: { requestId: 'req-789', timestamp: 1234567890 }
  // Все поля которые возвращает реальный API
};
```

## Антипаттерн 5: Тесты как запоздалая мысль

**Нарушение:**
```
✅ Реализация завершена
❌ Тесты не написаны
"Готово к тестированию"
```

**Исправление:**
```
Цикл TDD:
1. Напиши падающий тест
2. Реализуй для прохождения
3. Рефакторинг
4. ЗАТЕМ заявляй о завершении
```

## Когда моки становятся слишком сложными

**Предупреждающие знаки:**
- Настройка мока длиннее логики теста
- Мокируешь всё чтобы тест прошёл
- Моки пропускают методы которые имеют реальные компоненты
- Тест ломается когда мок изменяется

**Рассмотри:** Интеграционные тесты с реальными компонентами часто проще чем сложные моки

## TDD предотвращает эти антипаттерны

**Почему TDD помогает:**
1. **Пиши тест сначала** → Заставляет думать о том что реально тестируешь
2. **Наблюдай как падает** → Подтверждает что тест тестирует реальное поведение, не моки
3. **Минимальная реализация** → Методы только для тестов не проникают
4. **Реальные зависимости** → Видишь что реально нужно тесту перед мокированием

## Краткий справочник

| Антипаттерн | Исправление |
|--------------|-----|
| Утверждение на элементах мока | Тестируй реальный компонент или убери мок |
| Методы только для тестов в продакшне | Перемести в утилиты тестов |
| Мок без понимания | Сначала понимай зависимости, мокируй минимально |
| Неполные моки | Полностью отражай реальный API |
| Тесты как запоздалая мысль | TDD — тесты сначала |

## Итог

**Моки — инструменты для изоляции, а не то что тестируется.**

Если TDD показывает что ты тестируешь поведение моков — ты пошёл не туда.

Исправление: Тестируй реальное поведение или поставь под сомнение зачем вообще мокируешь.
