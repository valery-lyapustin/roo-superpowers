# Использование системы скиллов в Roo Code

## Обзор

Скиллы — это модульные инструкции, которые расширяют возможности Roo Code для конкретных задач.
Каждый скилл содержит проверенный рабочий процесс, паттерны и примеры для определённой области.
Принцип простой: **сначала найди скилл, потом делай задачу**.

## Железный закон

```
ПЕРЕД ЛЮБОЙ ЗАДАЧЕЙ — ПРОВЕРЬ СПИСОК СКИЛЛОВ
```

Если подходящий скилл найден — ты ОБЯЗАН его загрузить и следовать ему.
Это не опционально. Скиллы написаны на основе реального опыта и предотвращают известные ошибки.

## Обязательный рабочий процесс

**1. Проверь список скиллов** в начале сессии или запусти поиск по паттерну.

**2. Если подходящий скилл найден — ты ОБЯЗАН его использовать:**
- Загрузи скилл через инструмент `skill`
- Прочитай файл ПОЛНОСТЬЮ, не только фронтматтер
- Объяви: "Я загрузил скилл [Название] и использую его для [цели]"
- Следуй инструкциям точно

**Не рационализируй:**
- "Я помню этот скилл" — Скиллы обновляются. Загрузи актуальную версию.
- "Задача простая, скилл не нужен" — Простые задачи тоже имеют первопричины.
- "Это не считается задачей" — Считается. Найди и загрузи скилл.

## Скиллы с чеклистами

Если скилл содержит чеклист — ты ОБЯЗАН создать задачи в `update_todo_list` для КАЖДОГО пункта.

**Нельзя:**
- Держать чеклист в голове
- Пропускать создание задач "чтобы сэкономить время"
- Объединять несколько пунктов в одну задачу
- Отмечать выполненным без реального выполнения

**Почему:** Чеклисты без отслеживания = пропущенные шаги. Каждый раз.

## Объявление использования скилла

После загрузки скилла объяви его использование:

"Я загрузил скилл [Название] и использую его для [что делаю]."

**Примеры:**
- "Я загрузил скилл Мозговой штурм и использую его для проработки твоей идеи в дизайн."
- "Я загрузил скилл TDD и использую его для реализации этой фичи."
- "Я загрузил скилл Систематическая отладка и использую его для поиска первопричины."

## Все доступные скиллы

### Совместная работа

| Скилл | Когда применять |
|---|---|
| `brainstorming` | Партнёр описывает идею фичи или проекта — до написания кода |
| `writing-plans` | Дизайн готов, нужен детальный план реализации |
| `executing-plans` | Партнёр предоставил готовый план для выполнения |
| `subagent-driven-development` | Выполнение плана через свежих подагентов с ревью между задачами |
| `finishing-a-development-branch` | Реализация завершена, нужно решить как интегрировать работу |
| `requesting-code-review` | После завершения задачи или фичи — запросить ревью |
| `receiving-code-review` | Получено ревью — перед реализацией замечаний |
| `remembering-conversations` | Партнёр упоминает прошлые обсуждения, нужен исторический контекст |
| `dispatching-parallel-agents` | 3+ независимых задачи можно решить параллельно |
| `using-git-worktrees` | Нужна изолированная среда для фичи или эксперимента |

### Git и история изменений

| Скилл | Когда применять |
|---|---|
| `conventional-commits` | Нужно проверить сообщение, проанализировать изменения, подготовить план или безопасно создать атомарный Git-коммит по Conventional Commits |

### Отладка

| Скилл | Когда применять |
|---|---|
| `systematic-debugging` | Любой баг, падение теста, неожиданное поведение |
| `root-cause-tracing` | Ошибка глубоко в стеке вызовов, нужно найти источник |
| `defense-in-depth` | После нахождения бага — добавить многоуровневую защиту |
| `verification-before-completion` | Перед заявлением о завершении работы |

### Тестирование

| Скилл | Когда применять |
|---|---|
| `tdd` | Реализация любой фичи или исправление бага |
| `testing-anti-patterns` | При написании тестов, добавлении моков |
| `condition-based-waiting` | Тесты нестабильны, есть гонки условий или произвольные задержки |

### Архитектура

| Скилл | Когда применять |
|---|---|
| `preserving-productive-tensions` | Колебание между равно валидными подходами с разными приоритетами |

### Решение проблем

| Скилл | Когда применять |
|---|---|
| `when-stuck` | Застрял и не знаешь какую технику применить |
| `simplification-cascades` | Одно и то же реализовано 5+ способами, растут спецслучаи |
| `collision-zone-thinking` | Нужен прорыв, обычные подходы не подходят |
| `inversion-exercise` | Застрял на непроверяемых допущениях, чувствуешь "единственный путь" |
| `meta-pattern-recognition` | Один и тот же паттерн в 3+ разных местах |
| `scale-game` | Неясна масштабируемость, неясны граничные случаи |

### Исследование

| Скилл | Когда применять |
|---|---|
| `tracing-knowledge-lineages` | Вопрос "почему мы используем X", перед отказом от подходов |

## Соответствие инструментов

Скиллы из оригинального superpowers (Claude Code) используют другие инструменты.
В Roo Code их эквиваленты:

| Claude Code | Roo Code |
|---|---|
| `Task` (подагент) | `new_task` |
| `Skill` (загрузка скилла) | `skill` |
| `Read` | `read_file` |
| `Write` | `write_to_file` |
| `Edit` | `apply_diff` |
| `Bash` | `execute_command` |
| `TodoWrite` | `update_todo_list` |
| `WebSearch` | `mcp--context7--query-docs` |

## Режимы Roo Code

Выбирай режим под задачу — это влияет на то, какие файлы можно редактировать:

| Режим | Slug | Когда использовать |
|---|---|---|
| Архитектор | `architect` | Планирование, проектирование, `.md` файлы |
| Код | `code` | Написание и изменение кода |
| Отладка | `debug` | Поиск и исправление багов |
| Вопрос | `ask` | Объяснения, анализ, без изменений |
| Оркестратор | `orchestrator` | Сложные многошаговые задачи |

## Принципы работы со скиллами

1. **Загрузи скилл полностью** перед началом работы — не пропускай разделы
2. **Следуй инструкциям буквально** — скиллы написаны на основе реального опыта
3. **Не пропускай шаги** — особенно тесты и верификацию
4. **Сообщай о применении** — скажи пользователю, какой скилл используешь и почему
5. **Создавай задачи** для каждого пункта чеклиста через `update_todo_list`
