# Трассировка первопричины

## Обзор

Баги часто проявляются глубоко в стеке вызовов (git init в неправильной директории, файл создан в неправильном месте, база данных открыта с неправильным путём). Инстинкт — исправить там где появляется ошибка, но это лечение симптома.

**Основной принцип:** Трассируй назад через цепочку вызовов пока не найдёшь исходный триггер, затем исправляй в источнике.

## Когда использовать

**Используй когда:**
- Ошибка происходит глубоко в выполнении (не в точке входа)
- Стектрейс показывает длинную цепочку вызовов
- Неясно откуда взялись невалидные данные
- Нужно найти какой тест/код вызывает проблему

## Процесс трассировки

### 1. Наблюдай симптом
```
Ошибка: git init не удался в /home/user/project/packages/core
```

### 2. Найди непосредственную причину
**Какой код непосредственно вызывает это?**
```typescript
await execFileAsync('git', ['init'], { cwd: projectDir });
```

### 3. Спроси: Что вызвало это?
```typescript
WorktreeManager.createSessionWorktree(projectDir, sessionId)
  → вызван Session.initializeWorkspace()
  → вызван Session.create()
  → вызван тестом в Project.create()
```

### 4. Продолжай трассировать вверх
**Какое значение было передано?**
- `projectDir = ''` (пустая строка!)
- Пустая строка как `cwd` разрешается в `process.cwd()`
- Это директория исходного кода!

### 5. Найди исходный триггер
**Откуда взялась пустая строка?**
```typescript
const context = setupCoreTest(); // Возвращает { tempDir: '' }
Project.create('name', context.tempDir); // Доступ до beforeEach!
```

## Добавление стектрейсов

Когда не можешь трассировать вручную, добавь инструментацию:

```typescript
// Перед проблемной операцией
async function gitInit(directory: string) {
  const stack = new Error().stack;
  console.error('DEBUG git init:', {
    directory,
    cwd: process.cwd(),
    nodeEnv: process.env.NODE_ENV,
    stack,
  });

  await execFileAsync('git', ['init'], { cwd: directory });
}
```

**Критично:** Используй `console.error()` в тестах (не logger — может не показываться)

**Запусти и захвати:**
```bash
npm test 2>&1 | grep 'DEBUG git init'
```

**Анализируй стектрейсы:**
- Ищи имена тестовых файлов
- Найди номер строки вызывающей вызов
- Определи паттерн (тот же тест? тот же параметр?)

## Нахождение какой тест вызывает загрязнение

Если что-то появляется во время тестов но ты не знаешь какой тест:

```bash
# Запускай тесты по одному, останавливайся на первом загрязнителе
for test_file in $(find . -name "*.test.ts"); do
  echo "Тестирую: $test_file"
  npm test "$test_file" 2>&1 | grep -q "ЗАГРЯЗНЕНИЕ" && echo "НАЙДЕН: $test_file" && break
done
```

## Реальный пример: Пустой projectDir

**Симптом:** `.git` создан в `packages/core/` (исходный код)

**Цепочка трассировки:**
1. `git init` запускается в `process.cwd()` ← пустой параметр cwd
2. WorktreeManager вызван с пустым projectDir
3. Session.create() передал пустую строку
4. Тест обратился к `context.tempDir` до beforeEach
5. setupCoreTest() возвращает `{ tempDir: '' }` изначально

**Первопричина:** Инициализация переменной верхнего уровня обращающаяся к пустому значению

**Исправление:** Сделал tempDir геттером который бросает исключение если обращаются до beforeEach

**Также добавлена многоуровневая защита:**
- Уровень 1: Project.create() валидирует директорию
- Уровень 2: WorkspaceManager валидирует не пустой
- Уровень 3: Защита NODE_ENV отказывает в git init вне tmpdir
- Уровень 4: Логирование стектрейса перед git init

## Ключевой принцип

**НИКОГДА не исправляй только там где появляется ошибка.** Трассируй назад для нахождения исходного триггера.

## Советы по стектрейсам

**В тестах:** Используй `console.error()` а не logger — logger может быть подавлен
**Перед операцией:** Логируй до опасной операции, не после её провала
**Включай контекст:** Директория, cwd, переменные окружения, временные метки
**Захватывай стек:** `new Error().stack` показывает полную цепочку вызовов
