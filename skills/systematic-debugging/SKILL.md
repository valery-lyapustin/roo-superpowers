# Систематическая отладка

## Обзор

Случайные исправления тратят время и создают новые баги. Быстрые патчи маскируют глубинные проблемы.

**Основной принцип:** ВСЕГДА находи первопричину перед попыткой исправления. Исправление симптома — это провал.

**Нарушение буквы этого процесса — это нарушение его духа.**

## Железный закон

```
НИКАКИХ ИСПРАВЛЕНИЙ БЕЗ ПРЕДВАРИТЕЛЬНОГО ИССЛЕДОВАНИЯ ПЕРВОПРИЧИНЫ
```

Если ты не завершил Фазу 1 — ты не можешь предлагать исправления.

## Когда использовать

Используй при ЛЮБОЙ технической проблеме:
- Падения тестов
- Баги в продакшне
- Неожиданное поведение
- Проблемы с производительностью
- Ошибки сборки
- Проблемы интеграции

**Используй ОСОБЕННО когда:**
- Под давлением времени (срочность делает угадывание соблазнительным)
- "Одно быстрое исправление" кажется очевидным
- Ты уже пробовал несколько исправлений
- Предыдущее исправление не сработало
- Ты не полностью понимаешь проблему

**Не пропускай когда:**
- Проблема кажется простой (простые баги тоже имеют первопричины)
- Ты торопишься (спешка гарантирует переработку)
- Нужно исправить СЕЙЧАС (систематический подход быстрее хаотичного)

## Четыре фазы

Ты ОБЯЗАН завершить каждую фазу перед переходом к следующей.

### Фаза 1: Исследование первопричины

**ДО любой попытки исправления:**

1. **Внимательно читай сообщения об ошибках**
   - Не пропускай ошибки и предупреждения
   - Они часто содержат точное решение
   - Читай стектрейсы полностью
   - Записывай номера строк, пути к файлам, коды ошибок

2. **Воспроизводи стабильно**
   - Можешь ли ты вызвать это надёжно?
   - Каковы точные шаги?
   - Происходит ли это каждый раз?
   - Если не воспроизводится → собирай больше данных, не угадывай

3. **Проверяй последние изменения**
   - Что изменилось и могло вызвать это?
   - Git diff, последние коммиты
   - Новые зависимости, изменения конфигурации
   - Различия в окружении

4. **Собирай доказательства в многокомпонентных системах**

   **КОГДА система имеет несколько компонентов (CI → сборка → подпись, API → сервис → база данных):**

   **ДО предложения исправлений добавь диагностическую инструментацию:**
   ```
   Для КАЖДОЙ границы компонента:
     - Логируй что входит в компонент
     - Логируй что выходит из компонента
     - Проверяй передачу окружения/конфигурации
     - Проверяй состояние на каждом уровне

   Запусти один раз для сбора доказательств — ГДЕ ломается
   ЗАТЕМ анализируй доказательства для определения сломанного компонента
   ЗАТЕМ исследуй именно этот компонент
   ```

   **Пример (многоуровневая система):**
   ```bash
   # Уровень 1: Workflow
   echo "=== Секреты доступны в workflow: ==="
   echo "IDENTITY: ${IDENTITY:+УСТАНОВЛЕН}${IDENTITY:-НЕ УСТАНОВЛЕН}"

   # Уровень 2: Скрипт сборки
   echo "=== Переменные окружения в скрипте сборки: ==="
   env | grep IDENTITY || echo "IDENTITY не в окружении"

   # Уровень 3: Скрипт подписи
   echo "=== Состояние keychain: ==="
   security list-keychains
   security find-identity -v
   ```

   **Это показывает:** Какой уровень ломается (секреты → workflow ✓, workflow → сборка ✗)

5. **Трассируй поток данных**

   **КОГДА ошибка глубоко в стеке вызовов:**

   Смотри скилл `root-cause-tracing` для техники обратной трассировки.

   **Краткая версия:**
   - Откуда берётся плохое значение?
   - Что вызвало это с плохим значением?
   - Продолжай трассировать вверх до нахождения источника
   - Исправляй в источнике, не в симптоме

### Фаза 2: Анализ паттерна

**Найди паттерн перед исправлением:**

1. **Найди рабочие примеры**
   - Найди похожий рабочий код в той же кодовой базе
   - Что работает и похоже на сломанное?

2. **Сравни с эталонами**
   - Если реализуешь паттерн — читай эталонную реализацию ПОЛНОСТЬЮ
   - Не листай — читай каждую строку
   - Полностью понимай паттерн перед применением

3. **Определи различия**
   - Что отличается между рабочим и сломанным?
   - Перечисли каждое различие, каким бы малым оно ни было
   - Не предполагай "это не может иметь значения"

4. **Понимай зависимости**
   - Какие другие компоненты это нужны?
   - Какие настройки, конфигурация, окружение?
   - Какие допущения это делает?

### Фаза 3: Гипотеза и тестирование

**Научный метод:**

1. **Формулируй единственную гипотезу**
   - Формулируй чётко: "Я думаю X является первопричиной потому что Y"
   - Запиши это
   - Будь конкретным, не расплывчатым

2. **Тестируй минимально**
   - Делай НАИМЕНЬШЕЕ возможное изменение для проверки гипотезы
   - Одна переменная за раз
   - Не исправляй несколько вещей одновременно

3. **Верифицируй перед продолжением**
   - Сработало? Да → Фаза 4
   - Не сработало? Формируй НОВУЮ гипотезу
   - НЕ добавляй больше исправлений поверх

4. **Когда не знаешь**
   - Скажи "Я не понимаю X"
   - Не притворяйся что знаешь
   - Попроси помощи
   - Исследуй больше

### Фаза 4: Реализация

**Исправляй первопричину, не симптом:**

1. **Создай падающий тест**
   - Простейшее возможное воспроизведение
   - Автоматизированный тест если возможно
   - Одноразовый тестовый скрипт если нет фреймворка
   - ОБЯЗАТЕЛЕН перед исправлением
   - Смотри скилл `tdd` для написания правильных падающих тестов

2. **Реализуй единственное исправление**
   - Устраняй выявленную первопричину
   - ОДНО изменение за раз
   - Никаких "пока я здесь" улучшений
   - Никакого связанного рефакторинга

3. **Верифицируй исправление**
   - Тест теперь проходит?
   - Другие тесты не сломаны?
   - Проблема действительно решена?

4. **Если исправление не работает**
   - СТОП
   - Посчитай: Сколько исправлений ты пробовал?
   - Если < 3: Вернись к Фазе 1, переанализируй с новой информацией
   - **Если ≥ 3: СТОП и поставь под сомнение архитектуру (шаг 5 ниже)**
   - НЕ пытайся Исправление №4 без архитектурного обсуждения

5. **Если 3+ исправлений провалились: Поставь под сомнение архитектуру**

   **Паттерн, указывающий на архитектурную проблему:**
   - Каждое исправление обнаруживает новое общее состояние/связанность/проблему в другом месте
   - Исправления требуют "масштабного рефакторинга" для реализации
   - Каждое исправление создаёт новые симптомы в другом месте

   **СТОП и поставь под сомнение основы:**
   - Этот паттерн принципиально правильный?
   - Мы "придерживаемся его из чистой инерции"?
   - Стоит ли рефакторить архитектуру вместо продолжения исправления симптомов?

   **Обсуди с партнёром перед новыми попытками исправления**

   Это НЕ провальная гипотеза — это неправильная архитектура.

## Красные флаги — СТОП и следуй процессу

Если ловишь себя на мысли:
- "Быстрое исправление сейчас, исследую позже"
- "Просто попробую изменить X и посмотрю что будет"
- "Добавлю несколько изменений, запущу тесты"
- "Пропущу тест, проверю вручную"
- "Наверное X, давай исправлю это"
- "Не полностью понимаю, но это может сработать"
- "Паттерн говорит X, но я адаптирую по-другому"
- "Вот основные проблемы: [перечисляет исправления без исследования]"
- Предлагаешь решения до трассировки потока данных
- **"Ещё одна попытка исправления" (когда уже пробовал 2+)**
- **Каждое исправление обнаруживает новую проблему в другом месте**

**ВСЁ ЭТО означает: СТОП. Вернись к Фазе 1.**

**Если 3+ исправлений провалились:** Поставь под сомнение архитектуру (см. Фазу 4.5)

## Распространённые рационализации

| Отговорка | Реальность |
|--------|---------|
| "Проблема простая, процесс не нужен" | Простые проблемы тоже имеют первопричины. Процесс быстр для простых багов. |
| "Срочно, нет времени на процесс" | Систематическая отладка БЫСТРЕЕ чем угадывание. |
| "Просто попробую сначала, потом исследую" | Первое исправление задаёт паттерн. Делай правильно с самого начала. |
| "Напишу тест после подтверждения исправления" | Непроверенные исправления не держатся. Тест сначала доказывает это. |
| "Несколько исправлений сразу экономит время" | Нельзя изолировать что сработало. Вызывает новые баги. |
| "Эталон слишком длинный, адаптирую паттерн" | Частичное понимание гарантирует баги. Читай полностью. |
| "Вижу проблему, давай исправлю" | Видеть симптомы ≠ понимать первопричину. |
| "Ещё одна попытка" (после 2+ провалов) | 3+ провала = архитектурная проблема. Ставь под сомнение паттерн. |

## Краткий справочник

| Фаза | Ключевые действия | Критерий успеха |
|-------|---------------|------------------|
| **1. Первопричина** | Читай ошибки, воспроизводи, проверяй изменения, собирай доказательства | Понимаешь ЧТО и ПОЧЕМУ |
| **2. Паттерн** | Найди рабочие примеры, сравни | Определи различия |
| **3. Гипотеза** | Формулируй теорию, тестируй минимально | Подтверждена или новая гипотеза |
| **4. Реализация** | Создай тест, исправь, верифицируй | Баг решён, тесты проходят |

## Когда процесс показывает "нет первопричины"

Если систематическое исследование показывает что проблема действительно средовая, зависящая от времени или внешняя:

1. Ты завершил процесс
2. Документируй что исследовал
3. Реализуй соответствующую обработку (повтор, таймаут, сообщение об ошибке)
4. Добавь мониторинг/логирование для будущего исследования

**Но:** 95% случаев "нет первопричины" — это неполное исследование.

## Интеграция с другими скиллами

Этот скилл работает с:
- `root-cause-tracing` — Как трассировать назад через стек вызовов
- `defense-in-depth` — Добавить валидацию после нахождения первопричины
- `condition-based-waiting` — Заменить таймауты выявленные в Фазе 2
- `verification-before-completion` — Верифицировать что исправление сработало перед заявлением об успехе

## Реальный эффект

Из сессий отладки:
- Систематический подход: 15-30 минут до исправления
- Подход случайных исправлений: 2-3 часа хаоса
- Процент исправлений с первого раза: 95% против 40%
- Введённые новые баги: Почти ноль против частых
