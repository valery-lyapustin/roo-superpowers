# Многоуровневая защита (Defense-in-Depth)

## Обзор

Когда ты исправляешь баг вызванный невалидными данными, добавление валидации в одном месте кажется достаточным. Но эта единственная проверка может быть обойдена разными путями кода, рефакторингом или моками.

**Основной принцип:** Валидируй на КАЖДОМ уровне через который проходят данные. Сделай баг структурно невозможным.

## Почему несколько уровней

Единственная валидация: "Мы исправили баг"
Несколько уровней: "Мы сделали баг невозможным"

Разные уровни ловят разные случаи:
- Валидация на входе ловит большинство багов
- Бизнес-логика ловит граничные случаи
- Защита окружения предотвращает контекстно-специфические опасности
- Отладочное логирование помогает когда другие уровни не срабатывают

## Четыре уровня

### Уровень 1: Валидация точки входа
**Цель:** Отклонять явно невалидный ввод на границе API

```typescript
function createProject(name: string, workingDirectory: string) {
  if (!workingDirectory || workingDirectory.trim() === '') {
    throw new Error('workingDirectory не может быть пустым');
  }
  if (!existsSync(workingDirectory)) {
    throw new Error(`workingDirectory не существует: ${workingDirectory}`);
  }
  if (!statSync(workingDirectory).isDirectory()) {
    throw new Error(`workingDirectory не является директорией: ${workingDirectory}`);
  }
  // ... продолжай
}
```

### Уровень 2: Валидация бизнес-логики
**Цель:** Убедиться что данные имеют смысл для этой операции

```typescript
function initializeWorkspace(projectDir: string, sessionId: string) {
  if (!projectDir) {
    throw new Error('projectDir обязателен для инициализации рабочего пространства');
  }
  // ... продолжай
}
```

### Уровень 3: Защита окружения
**Цель:** Предотвращать опасные операции в специфических контекстах

```typescript
async function gitInit(directory: string) {
  // В тестах отказывай в git init вне временных директорий
  if (process.env.NODE_ENV === 'test') {
    const normalized = normalize(resolve(directory));
    const tmpDir = normalize(resolve(tmpdir()));

    if (!normalized.startsWith(tmpDir)) {
      throw new Error(
        `Отказ в git init вне temp директории во время тестов: ${directory}`
      );
    }
  }
  // ... продолжай
}
```

### Уровень 4: Отладочная инструментация
**Цель:** Захватывать контекст для криминалистики

```typescript
async function gitInit(directory: string) {
  const stack = new Error().stack;
  logger.debug('Собираюсь выполнить git init', {
    directory,
    cwd: process.cwd(),
    stack,
  });
  // ... продолжай
}
```

## Применение паттерна

Когда находишь баг:

1. **Трассируй поток данных** — Откуда берётся плохое значение? Где используется?
2. **Составь карту всех контрольных точек** — Перечисли каждую точку через которую проходят данные
3. **Добавь валидацию на каждом уровне** — Вход, бизнес, окружение, отладка
4. **Тестируй каждый уровень** — Попробуй обойти уровень 1, убедись что уровень 2 ловит

## Пример из сессии

Баг: Пустой `projectDir` вызвал `git init` в исходном коде

**Поток данных:**
1. Настройка теста → пустая строка
2. `Project.create(name, '')`
3. `WorkspaceManager.createWorkspace('')`
4. `git init` запускается в `process.cwd()`

**Четыре добавленных уровня:**
- Уровень 1: `Project.create()` валидирует не пустой/существует/доступен для записи
- Уровень 2: `WorkspaceManager` валидирует что projectDir не пустой
- Уровень 3: `WorktreeManager` отказывает в git init вне tmpdir в тестах
- Уровень 4: Логирование стектрейса перед git init

**Результат:** Все 1847 тестов прошли, баг невозможно воспроизвести

## Ключевое понимание

Все четыре уровня были необходимы. Во время тестирования каждый уровень ловил баги которые другие пропускали:
- Разные пути кода обходили валидацию на входе
- Моки обходили проверки бизнес-логики
- Граничные случаи на разных платформах требовали защиты окружения
- Отладочное логирование выявляло структурное неправильное использование

**Не останавливайся на одной точке валидации.** Добавляй проверки на каждом уровне.
