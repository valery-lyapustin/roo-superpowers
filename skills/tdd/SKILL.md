# Разработка через тестирование (TDD)

## Обзор

Сначала пиши тест. Наблюдай как он падает. Пиши минимальный код для прохождения.

**Основной принцип:** Если ты не наблюдал как тест падает — ты не знаешь, тестирует ли он правильную вещь.

**Нарушение буквы правил — это нарушение их духа.**

## Когда использовать

**Всегда:**
- Новые фичи
- Исправления багов
- Рефакторинг
- Изменения поведения

**Исключения (спроси партнёра):**
- Одноразовые прототипы
- Сгенерированный код
- Конфигурационные файлы

Думаешь "пропустить TDD на этот раз"? Стоп. Это рационализация.

## Железный закон

```
НИКАКОГО ПРОДАКШН-КОДА БЕЗ ПРЕДВАРИТЕЛЬНОГО ПАДАЮЩЕГО ТЕСТА
```

Написал код до теста? Удали его. Начни заново.

**Без исключений:**
- Не оставляй как "справочник"
- Не "адаптируй" его при написании тестов
- Не смотри на него
- Удалить значит удалить

Реализуй заново с нуля от тестов. Точка.

## Красный-Зелёный-Рефакторинг

```
КРАСНЫЙ → ЗЕЛЁНЫЙ → РЕФАКТОРИНГ → повтор
```

### КРАСНЫЙ — Пиши падающий тест

Пиши один минимальный тест, показывающий что должно происходить.

**Хорошо:**
```typescript
test('повторяет неудачные операции 3 раза', async () => {
  let попыток = 0;
  const операция = () => {
    попыток++;
    if (попыток < 3) throw new Error('ошибка');
    return 'успех';
  };

  const результат = await повторитьОперацию(операция);

  expect(результат).toBe('успех');
  expect(попыток).toBe(3);
});
```
Чёткое название, тестирует реальное поведение, одна вещь.

**Плохо:**
```typescript
test('повтор работает', async () => {
  const mock = jest.fn()
    .mockRejectedValueOnce(new Error())
    .mockRejectedValueOnce(new Error())
    .mockResolvedValueOnce('успех');
  await повторитьОперацию(mock);
  expect(mock).toHaveBeenCalledTimes(3);
});
```
Расплывчатое название, тестирует мок а не код.

**Требования:**
- Одно поведение
- Чёткое название
- Реальный код (моки только если неизбежно)

### Верифицируй КРАСНЫЙ — Наблюдай как падает

**ОБЯЗАТЕЛЬНО. Никогда не пропускай.**

```bash
npm test путь/к/тесту.test.ts
```

Подтверди:
- Тест падает (не ошибка)
- Сообщение об ошибке ожидаемое
- Падает потому что фича отсутствует (не опечатки)

**Тест проходит?** Ты тестируешь существующее поведение. Исправь тест.

**Тест выдаёт ошибку?** Исправь ошибку, перезапускай пока не будет правильного падения.

### ЗЕЛЁНЫЙ — Минимальный код

Пиши простейший код для прохождения теста.

**Хорошо:**
```typescript
async function повторитьОперацию<T>(fn: () => Promise<T>): Promise<T> {
  for (let i = 0; i < 3; i++) {
    try {
      return await fn();
    } catch (e) {
      if (i === 2) throw e;
    }
  }
  throw new Error('недостижимо');
}
```
Ровно столько чтобы пройти.

**Плохо:**
```typescript
async function повторитьОперацию<T>(
  fn: () => Promise<T>,
  опции?: {
    максПовторов?: number;
    задержка?: 'линейная' | 'экспоненциальная';
    приПовторе?: (попытка: number) => void;
  }
): Promise<T> {
  // YAGNI — не нужно сейчас
}
```
Переусложнено.

Не добавляй фичи, не рефакторь другой код, не "улучшай" сверх теста.

### Верифицируй ЗЕЛЁНЫЙ — Наблюдай как проходит

**ОБЯЗАТЕЛЬНО.**

```bash
npm test путь/к/тесту.test.ts
```

Подтверди:
- Тест проходит
- Другие тесты всё ещё проходят
- Вывод чистый (нет ошибок, предупреждений)

**Тест падает?** Исправь код, не тест.

**Другие тесты падают?** Исправь сейчас.

### РЕФАКТОРИНГ — Чисти

Только после зелёного:
- Убирай дублирование
- Улучшай названия
- Выделяй вспомогательные функции

Держи тесты зелёными. Не добавляй поведение.

### Повтор

Следующий падающий тест для следующей фичи.

## Хорошие тесты

| Качество | Хорошо | Плохо |
|---------|------|-----|
| **Минимальный** | Одна вещь. "и" в названии? Раздели. | `test('валидирует email и домен и пробелы')` |
| **Чёткий** | Название описывает поведение | `test('тест1')` |
| **Показывает намерение** | Демонстрирует желаемый API | Скрывает что должен делать код |

## Почему порядок важен

**"Напишу тесты после чтобы проверить что работает"**

Тесты написанные после кода проходят немедленно. Немедленное прохождение ничего не доказывает:
- Может тестировать не то
- Может тестировать реализацию, не поведение
- Может пропустить граничные случаи которые ты забыл
- Ты никогда не видел как он ловит баг

Тест-сначала заставляет тебя видеть падение теста, доказывая что он что-то тестирует.

**"Уже вручную протестировал все граничные случаи"**

Ручное тестирование — это ad-hoc. Ты думаешь что протестировал всё, но:
- Нет записи что тестировал
- Нельзя перезапустить при изменении кода
- Легко забыть случаи под давлением
- "Работало когда пробовал" ≠ исчерпывающее

Автоматизированные тесты систематичны. Они запускаются одинаково каждый раз.

**"Удалять X часов работы расточительно"**

Ошибка невозвратных затрат. Время уже потрачено. Твой выбор сейчас:
- Удалить и переписать с TDD (ещё X часов, высокая уверенность)
- Оставить и добавить тесты после (30 минут, низкая уверенность, вероятные баги)

"Расточительство" — это хранить код которому нельзя доверять.

## Распространённые рационализации

| Отговорка | Реальность |
|--------|---------|
| "Слишком просто для теста" | Простой код ломается. Тест занимает 30 секунд. |
| "Напишу тест после" | Тесты проходящие немедленно ничего не доказывают. |
| "Тесты после достигают тех же целей" | Тесты-после = "что это делает?" Тесты-сначала = "что это должно делать?" |
| "Уже вручную протестировал" | Ad-hoc ≠ систематично. Нет записи, нельзя перезапустить. |
| "Удалять X часов расточительно" | Ошибка невозвратных затрат. Хранить непроверенный код — технический долг. |
| "Оставлю как справочник, напишу тесты сначала" | Ты адаптируешь его. Это тестирование после. Удалить значит удалить. |
| "Нужно сначала исследовать" | Хорошо. Выброси исследование, начни с TDD. |
| "Тест сложный = дизайн неясный" | Слушай тест. Сложно тестировать = сложно использовать. |
| "TDD замедлит меня" | TDD быстрее отладки. Прагматично = тест-сначала. |

## Красные флаги — СТОП и начни заново

- Код до теста
- Тест после реализации
- Тест проходит немедленно
- Не можешь объяснить почему тест падал
- Тесты добавлены "позже"
- Рационализируешь "только на этот раз"
- "Уже вручную протестировал"
- "Тесты после достигают той же цели"
- "Это о духе, не ритуале"
- "Оставлю как справочник" или "адаптирую существующий код"
- "Уже потратил X часов, удалять расточительно"
- "TDD догматично, я прагматичен"
- "Это другое потому что..."

**Всё это означает: Удали код. Начни заново с TDD.**

## Пример: Исправление бага

**Баг:** Принимается пустой email

**КРАСНЫЙ**
```typescript
test('отклоняет пустой email', async () => {
  const результат = await отправитьФорму({ email: '' });
  expect(результат.ошибка).toBe('Email обязателен');
});
```

**Верифицируй КРАСНЫЙ**
```bash
$ npm test
FAIL: ожидалось 'Email обязателен', получено undefined
```

**ЗЕЛЁНЫЙ**
```typescript
function отправитьФорму(данные: ДанныеФормы) {
  if (!данные.email?.trim()) {
    return { ошибка: 'Email обязателен' };
  }
  // ...
}
```

**Верифицируй ЗЕЛЁНЫЙ**
```bash
$ npm test
PASS
```

**РЕФАКТОРИНГ**
Выдели валидацию для нескольких полей если нужно.

## Чеклист верификации

Перед отметкой работы как завершённой:

- [ ] Каждая новая функция/метод имеет тест
- [ ] Наблюдал как каждый тест падает перед реализацией
- [ ] Каждый тест падал по ожидаемой причине (фича отсутствует, не опечатка)
- [ ] Написал минимальный код для прохождения каждого теста
- [ ] Все тесты проходят
- [ ] Вывод чистый (нет ошибок, предупреждений)
- [ ] Тесты используют реальный код (моки только если неизбежно)
- [ ] Граничные случаи и ошибки покрыты

Не можешь отметить все пункты? Ты пропустил TDD. Начни заново.

## Когда застрял

| Проблема | Решение |
|---------|----------|
| Не знаешь как тестировать | Напиши желаемый API. Напиши утверждение сначала. Спроси партнёра. |
| Тест слишком сложный | Дизайн слишком сложный. Упрости интерфейс. |
| Нужно мокировать всё | Код слишком связан. Используй внедрение зависимостей. |
| Огромная настройка теста | Выдели вспомогательные функции. Всё ещё сложно? Упрости дизайн. |

## Интеграция с отладкой

Нашёл баг? Напиши падающий тест воспроизводящий его. Следуй циклу TDD. Тест доказывает исправление и предотвращает регрессию.

Никогда не исправляй баги без теста.

## Финальное правило

```
Продакшн-код → тест существует и падал сначала
Иначе → это не TDD
```

Без исключений без разрешения партнёра.
