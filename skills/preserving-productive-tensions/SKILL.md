# Сохранение продуктивных противоречий

## Обзор

Некоторые противоречия — это не проблемы для решения, а ценная информация для сохранения. Когда несколько подходов действительно валидны в разных контекстах, принудительный выбор уничтожает гибкость.

**Основной принцип:** Сохраняй противоречия раскрывающие контекстную зависимость. Принудительно разрешай только когда необходимо.

## Распознавание продуктивных противоречий

**Противоречие продуктивно когда:**
- Оба подхода оптимизируют разные валидные приоритеты (стоимость против задержки, простота против фич)
- "Лучший" выбор зависит от контекста развёртывания, а не технического превосходства
- Разные пользователи/развёртывания выбрали бы по-разному
- Компромисс реален и не исчезнет с умной инженерией
- Заинтересованные стороны имеют конфликтующие валидные опасения

**Противоречие требует разрешения когда:**
- Стоимость реализации сохранения обоих запретительна
- Подходы фундаментально конфликтуют (не могут сосуществовать)
- Есть явное техническое превосходство для этого конкретного случая
- Это дверь в одну сторону (выбор блокирует архитектуру)
- Сохранение обоих добавляет сложность без ценности

## Паттерны сохранения

### Паттерн 1: Конфигурация
Сделай выбор конфигурируемым вместо встроенного в архитектуру:

```python
class Config:
    mode: Literal["optimize_cost", "optimize_latency"]
    # Каждый режим получает чистую, простую реализацию
```

**Когда использовать:** Оба подхода архитектурно совместимы, переключение — решение времени выполнения

### Паттерн 2: Параллельные реализации
Поддерживай оба как отдельные чистые модули с общим контрактом:

```python
# processor/batch.py — оптимизирует стоимость
# processor/stream.py — оптимизирует задержку
# Оба реализуют: def process(data) -> Result
```

**Когда использовать:** Подходы значительно расходятся, но разделяют один интерфейс

### Паттерн 3: Задокументированный компромисс
Явно фиксируй противоречие в документации/записях решений:

```markdown
## Неразрешённое противоречие: Стратегия аутентификации

**Вариант A: JWT** — Без состояния, легко масштабируется, но отзыв токена сложен
**Вариант B: Сессии** — Лёгкий отзыв, но требует общего состояния

**Почему неразрешено:** Разные развёртывания нуждаются в разных компромиссах
**Решение отложено до:** Конфигурации развёртывания
**Триггер пересмотра:** Если 80% развёртываний выбирают один вариант
```

**Когда использовать:** Нельзя сохранить оба в коде, но нужно задокументировать что выбор был намеренным

## Красные флаги — Ты принудительно разрешаешь

- Спрашиваешь "что лучше?" когда оба валидны
- "Нам нужно выбрать одно" без объяснения почему
- Выбираешь на основе своего предпочтения против контекста пользователя
- Разрешаешь противоречия "чтобы двигаться вперёд" когда их сохранение И ЕСТЬ прогресс
- Принудительный консенсус когда разнообразие ценно

**Всё это означает: СТОП. Рассмотри сохранение противоречия.**

## Когда принудительно разрешать

**СЛЕДУЕТ принудительно разрешать когда:**

1. **Стоимость реализации запретительна**
   - Создание/поддержка обоих значительно замедлит разработку
   - У команды нет пропускной способности для параллельных подходов

2. **Фундаментальный конфликт**
   - Подходы делают противоречивые архитектурные допущения
   - Нельзя чисто разделить ответственность

3. **Явное техническое превосходство**
   - Один подход объективно лучше для этого конкретного контекста
   - Не "я предпочитаю X" а "X решает наши ограничения, Y нет"

4. **Дверь в одну сторону**
   - Выбор блокирует нас в архитектуре
   - Миграция между вариантами была бы дорогой

5. **Простота требует выбора**
   - Сохранение обоих реально добавляет сложность
   - YAGNI: Не строй оба если нужен только один

**Спрашивай явно:** "Мне выбрать один, или сохранить оба как варианты?"

## Формат документации

При сохранении противоречий документируй чётко:

```markdown
## Противоречие: [Название]

**Контекст:** [Почему это противоречие существует]

**Вариант A:** [Подход]
- Оптимизирует: [Приоритет]
- Компромисс: [Стоимость]
- Лучше когда: [Контекст]

**Вариант B:** [Подход]
- Оптимизирует: [Другой приоритет]
- Компромисс: [Другая стоимость]
- Лучше когда: [Другой контекст]

**Стратегия сохранения:** [Конфигурация/Параллельная/Задокументированная]

**Триггер разрешения:** [Условия которые заставят выбрать одно]
```

## Примеры

### Продуктивное противоречие (Сохранить)
"Оптимизировать стоимость или задержку?"
- **Ответ:** Сделай конфигурируемым — разные развёртывания нуждаются в разных компромиссах

### Техническое решение (Разрешить)
"Использовать SSE или WebSockets?"
- **Ответ:** SSE — нам нужна только односторонняя коммуникация, более простая реализация

### Бизнес-решение (Отложить)
"Поддерживать офлайн-режим?"
- **Ответ:** Не сохраняй оба — спроси заинтересованную сторону решить на основе потребностей пользователей

## Помни

- Противоречия между валидными приоритетами — это фичи, не баги
- Преждевременный консенсус уничтожает ценную гибкость
- Конфигурация > принудительный выбор (когда разумно)
- Явно документируй компромиссы
- Разрешение нормально когда обосновано
