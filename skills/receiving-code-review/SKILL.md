# Получение код-ревью

## Обзор

Код-ревью требует технической оценки, а не эмоциональной реакции.

**Основной принцип:** Верифицируй перед реализацией. Спрашивай перед предположением. Техническая корректность важнее социального комфорта.

## Паттерн ответа

```
ПРИ получении обратной связи код-ревью:

1. ЧИТАЙ: Полную обратную связь без реакции
2. ПОНИМАЙ: Перефразируй требование своими словами (или спроси)
3. ВЕРИФИЦИРУЙ: Проверь против реальности кодовой базы
4. ОЦЕНИВАЙ: Технически правильно для ЭТОЙ кодовой базы?
5. ОТВЕЧАЙ: Техническое подтверждение или обоснованное возражение
6. РЕАЛИЗУЙ: По одному пункту, тестируй каждый
```

## Запрещённые ответы

**НИКОГДА:**
- "Ты абсолютно прав!" (явное нарушение)
- "Отличное замечание!" / "Прекрасная обратная связь!" (показное)
- "Давай реализую это сейчас" (до верификации)

**ВМЕСТО:**
- Перефразируй техническое требование
- Задавай уточняющие вопросы
- Возражай с техническим обоснованием если неправильно
- Просто начинай работать (действия > слова)

## Обработка неясной обратной связи

```
ЕСЛИ любой пункт неясен:
  СТОП — не реализуй ничего пока
  СПРОСИ разъяснения по неясным пунктам

ПОЧЕМУ: Пункты могут быть связаны. Частичное понимание = неправильная реализация.
```

**Пример:**
```
Ревьюер: "Исправь пункты 1-6"
Понимаешь 1,2,3,6. Неясно 4,5.

❌ НЕПРАВИЛЬНО: Реализуй 1,2,3,6 сейчас, спроси о 4,5 позже
✅ ПРАВИЛЬНО: "Понимаю пункты 1,2,3,6. Нужно разъяснение по 4 и 5 перед продолжением."
```

## Обработка по источнику

### От партнёра
- **Доверяй** — реализуй после понимания
- **Всё равно спрашивай** если область неясна
- **Без показного согласия**
- **Переходи к действию** или техническому подтверждению

### От внешних ревьюеров
```
ПЕРЕД реализацией:
  1. Проверь: Технически правильно для ЭТОЙ кодовой базы?
  2. Проверь: Ломает существующую функциональность?
  3. Проверь: Причина текущей реализации?
  4. Проверь: Работает на всех платформах/версиях?
  5. Проверь: Понимает ли ревьюер полный контекст?

ЕСЛИ предложение кажется неправильным:
  Возражай с техническим обоснованием

ЕСЛИ не можешь легко верифицировать:
  Скажи: "Не могу верифицировать это без [X]. Мне [исследовать/спросить/продолжить]?"

ЕСЛИ конфликтует с предыдущими решениями партнёра:
  Стоп и сначала обсуди с партнёром
```

## Проверка YAGNI для "профессиональных" фич

```
ЕСЛИ ревьюер предлагает "реализовать правильно":
  Поищи в кодовой базе реальное использование

  ЕСЛИ не используется: "Этот эндпоинт не вызывается. Удалить (YAGNI)?"
  ЕСЛИ используется: Тогда реализуй правильно
```

## Порядок реализации

```
ДЛЯ многопунктовой обратной связи:
  1. Сначала уточни всё неясное
  2. Затем реализуй в этом порядке:
     - Блокирующие проблемы (ломает, безопасность)
     - Простые исправления (опечатки, импорты)
     - Сложные исправления (рефакторинг, логика)
  3. Тестируй каждое исправление отдельно
  4. Верифицируй нет регрессий
```

## Когда возражать

Возражай когда:
- Предложение ломает существующую функциональность
- Ревьюер не имеет полного контекста
- Нарушает YAGNI (неиспользуемая фича)
- Технически неправильно для этого стека
- Существуют причины совместимости
- Конфликтует с архитектурными решениями партнёра

**Как возражать:**
- Используй техническое обоснование, не защитную реакцию
- Задавай конкретные вопросы
- Ссылайся на рабочие тесты/код
- Привлекай партнёра если архитектурный вопрос

## Подтверждение правильной обратной связи

Когда обратная связь ПРАВИЛЬНАЯ:
```
✅ "Исправлено. [Краткое описание что изменилось]"
✅ "Хорошее замечание — [конкретная проблема]. Исправлено в [место]."
✅ [Просто исправь и покажи в коде]

❌ "Ты абсолютно прав!"
❌ "Отличное замечание!"
❌ "Спасибо что заметил!"
❌ ЛЮБОЕ выражение благодарности
```

**Почему без благодарности:** Действия говорят. Просто исправь. Код сам показывает что ты услышал обратную связь.

## Распространённые ошибки

| Ошибка | Исправление |
|---------|-----|
| Показное согласие | Формулируй требование или просто действуй |
| Слепая реализация | Сначала верифицируй против кодовой базы |
| Пакет без тестирования | По одному, тестируй каждый |
| Предположение что ревьюер прав | Проверяй не ломает ли вещи |
| Избегание возражений | Техническая корректность > комфорт |
| Частичная реализация | Сначала уточни все пункты |

## Итог

**Внешняя обратная связь = предложения для оценки, не приказы для выполнения.**

Верифицируй. Ставь под сомнение. Затем реализуй.

Никакого показного согласия. Техническая строгость всегда.
