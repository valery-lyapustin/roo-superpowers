# Трассировка линий знаний

## Обзор

Идеи имеют историю. Понимание почему мы пришли к текущим подходам — и что пробовалось раньше — предотвращает повторение провалов и переоткрывает заброшенные решения.

**Основной принцип:** Перед оценкой текущих подходов или предложением "новых" — трассируй их линию.

## Когда трассировать линии

**Трассируй перед:**
- Предложением заменить существующий подход (сначала понимай почему он существует)
- Отклонением "старых" паттернов (они могли быть заброшены по неправильным причинам)
- Реализацией "новых" идей (они могут быть возрождениями стоящими переосмысления)
- Объявлением чего-то "лучшей практикой" (понимай его эволюцию)

**Красные флаги запускающие трассировку линий:**
- "Это кажется переусложнённым" (было ли проще раньше? почему выросло?)
- "Почему бы просто не..." (кто-то вероятно пробовал, что случилось?)
- "Это современный способ" (что нас научил старый способ?)
- "Нам следует переключиться на X" (что изначально отвело нас от X?)

## Техники трассировки

### Техника 1: Археология решений

Ищи когда/почему был выбран текущий подход:

1. **Проверяй записи решений** (общие места: `docs/decisions/`, `docs/adr/`, `.decisions/`, записи архитектурных решений)
2. **Ищи в разговорах** (скилл `remembering-conversations`)
3. **Git-археология** (`git log --all --full-history -- путь/к/файлу`)
4. **Спрашивай человека написавшего это** (если доступен)

**Документируй:**
```markdown
## Линия: [Текущий подход]

**Когда принят:** [Дата/коммит]
**Почему принят:** [Исходная проблема которую решал]
**Что заменил:** [Предыдущий подход]
**Почему заменил:** [Что было не так со старым подходом]
**Контекст который двигал изменение:** [Внешние факторы, новые требования]
```

### Техника 2: Анализ неудачных попыток

Когда кто-то говорит "мы пробовали X и не сработало":

**Не предполагай:** X фундаментально неправильный
**Вместо трассируй:**
1. **Каков был контекст?** (ограничения которые больше не применяются)
2. **Что конкретно провалилось?** (весь подход или один аспект?)
3. **Почему провалилось тогда?** (технологические лимиты, ограничения команды, давление времени)
4. **Изменился ли контекст?** (новые инструменты, другие требования, больше опыта)

**Документируй:**
```markdown
## Неудачная попытка: [Подход]

**Когда пробовали:** [Временной период]
**Почему пробовали:** [Исходная мотивация]
**Что провалилось:** [Конкретный режим провала]
**Почему провалилось:** [Первопричина, не симптомы]
**Контекст тогда:** [Ограничения существовавшие тогда]
**Контекст сейчас:** [Что изменилось сегодня]
**Стоит переосмыслить?:** [Да/Нет + обоснование]
```

### Техника 3: Обнаружение возрождений

При оценке "новых" подходов:

1. **Ищи исторические прецеденты** (пробовалось ли это раньше под другим названием?)
2. **Определяй что действительно новое** (против того что переименовано)
3. **Понимай почему умерло** (если это возрождение)
4. **Проверяй существуют ли условия воскрешения** (достаточно ли изменился контекст?)

**Общие паттерны возрождений:**
- Микросервисы ← Сервис-ориентированная архитектура ← Распределённые объекты
- GraphQL ← SOAP ← RPC
- Serverless ← CGI-скрипты ← Облачные функции
- NoSQL ← Плоские файлы ← Документные хранилища

**Спрашивай:** "Что мы узнали от предыдущего воплощения?"

### Техника 4: Картирование смены парадигм

Когда произошли крупные архитектурные изменения:

**Картируй переход:**
```markdown
## Смена парадигмы: От [Старого] к [Новому]

**Мышление до сдвига:** [Как думали о проблеме]
**Катализатор:** [Что вызвало сдвиг]
**Мышление после сдвига:** [Как думаем сейчас]
**Что получили:** [Новые возможности]
**Что потеряли:** [Старые возможности принесённые в жертву]
**Сохранённые уроки:** [Что сохранили от старой парадигмы]
**Забытые уроки:** [Что может понадобиться переучить]
```

## Стратегии поиска

**Где искать линии:**

1. **Записи решений** (общие места: `docs/decisions/`, `docs/adr/`, `.adr/`, или ищи "ADR", "decision record")
2. **История разговоров** (поиск через скилл `remembering-conversations`)
3. **Git-история** (`git log --grep="ключевое-слово"`, `git blame`)
4. **Обсуждения задач/PR** (история задач GitHub/GitLab)
5. **Эволюция документации** (`git log -- docs/`)
6. **Знания команды** (спрашивай: "Кто-нибудь пробовал это раньше?")

**Паттерны поиска:**
```bash
# Найти когда подход был введён
git log --all --grep="introduce.*caching"

# Найти что заменил файл
git log --diff-filter=D --summary | grep pattern

# Найти обсуждение заброшенного подхода
git log --all --grep="remove.*websocket"
```

## Красные флаги — Ты игнорируешь историю

- "Давай просто перепишем это" (без понимания почему это сложно)
- "Старый способ был очевидно неправильным" (без понимания контекста)
- "Никто больше не использует X" (без проверки почему умерло)
- Отклонение подходов потому что они "старые" (возраст ≠ качество)
- Принятие подходов потому что они "новые" (новизна ≠ качество)

**Всё это означает: СТОП. Сначала трассируй линию.**

## Когда переопределять историю

**МОЖНО игнорировать линию когда:**

1. **Контекст фундаментально изменился**
   - Технология которой не существовало теперь доступна
   - Ограничения которые форсировали решения больше не применяются
   - Команда имеет другие возможности сейчас

2. **Мы узнали критические уроки**
   - Понимание в отрасли эволюционировало
   - Прошлая попытка научила что избегать
   - Лучшие паттерны появились и были доказаны

3. **Исходное обоснование было ошибочным**
   - Основано на допущениях позже доказанных неправильными
   - Карго-культ без понимания
   - Движимо модой, а не потребностями

**Но документируй ПОЧЕМУ переопределяешь:** Будущее ты должно знать что это было намеренным, а не невежественным.

## Примеры

### Хорошая трассировка линии
"Мы использовали XML до JSON. XML умер потому что многословность вредила опыту разработчика. Но пространства имён XML решали реальную проблему. Если мы столкнёмся с конфликтами пространств имён в JSON, нам следует изучить как XML решал это, а не изобретать заново."

### Плохое игнорирование истории
"REST старый, давай используем GraphQL." (Игнорирует: Почему REST победил над SOAP? Какие проблемы он хорошо решает? Эти проблемы исчезли?)

### Возрождение с контекстом
"Мы пробовали клиентскую маршрутизацию в 2010, отказались из-за плохой поддержки браузеров. Теперь когда поддержка универсальна и у нас лучшие инструменты, стоит переосмыслить с извлечёнными уроками."

## Помни

- Текущие подходы существуют по причинам (трассируй эти причины)
- Прошлые провалы могут работать сейчас (контекст меняется)
- "Новые" подходы могут быть возрождениями (проверяй прецеденты)
- Эволюция учит (изучай переходы)
- Незнание истории = обречён её повторять
