# Conventional Commits

## Обзор

Создавай небольшие, логически цельные и понятные человеку и автоматическим инструментам Git-коммиты. Сначала исследуй фактические изменения и правила проекта, затем предложи план коммита, получи явное подтверждение и только после этого меняй индекс Git и создавай коммит.

Скилл работает не только для реального коммита. Он также помогает проверить уже написанное сообщение или подготовить корректный текст коммита без изменения индекса. Для junior-разработчика это важное разделение: сформулировать сообщение — безопасная читающая операция, а создать коммит — уже изменение истории проекта.

**Основной принцип:** Сначала режим работы и факты, затем атомарный план, подтверждение, проверки и только потом коммит.

**Объяви в начале:** "Я использую скилл Conventional Commits для безопасной подготовки атомарного коммита."

## Железный закон

```text
НИКАКОГО РЕАЛЬНОГО КОММИТА БЕЗ ПРОСМОТРА ФАКТИЧЕСКОГО DIFF, АКТУАЛЬНОГО ПЛАНА, УСПЕШНЫХ РЕЛЕВАНТНЫХ ПРОВЕРОК И ЯВНОГО ПОДТВЕРЖДЕНИЯ ПОЛЬЗОВАТЕЛЯ
```

До подтверждения выполняй только читающий анализ. Никогда не подменяй подтверждение предположением вроде "пользователь попросил закоммитить, значит всё разрешено".

Если пользователь просит только проверить или написать сообщение, не меняй индекс, рабочее дерево, историю и remote. Дай сообщение, объясни выбор type/scope и остановись.

## Режимы работы

В начале явно выбери один режим. Это защищает от типичной ошибки, когда просьба "помоги с сообщением" случайно превращается в staging и коммит.

| Режим | Когда применять | Что можно делать | Где остановиться |
|---|---|---|---|
| Проверка сообщения | Пользователь дал готовый заголовок или полный текст коммита | Проверить грамматику Conventional Commits, type, scope, breaking change, trailers и стиль | Вернуть исправленное сообщение и замечания |
| Подготовка сообщения | Пользователь просит придумать сообщение по текущим изменениям или по описанию | Прочитать факты, предложить одно или несколько сообщений, объяснить атомарность | Не выполнять staging и commit |
| Создание коммита | Пользователь явно просит создать Git-коммит | Выполнить полный процесс: diff, секреты, атомарный план, подтверждение, staging, проверки, commit | Сообщить результат и остаточные изменения |

Если режим неясен, выбери самый безопасный: подготовка сообщения без изменения состояния репозитория. Реальный коммит делай только когда пользователь прямо подтвердил конкретный план.

## Формат сообщения

Используй грамматику Conventional Commits 1.0.0 без несовместимых расширений:

```text
<type>[optional scope][optional !]: <description>

[optional body]

[optional footer(s)]
```

- `type` обязателен и описывает намерение изменения.
- `scope` необязателен, заключается в круглые скобки и называет устойчивую область проекта.
- `!` ставится непосредственно перед `:` и сигнализирует о несовместимом изменении.
- После `:` ставится ровно один пробел.
- `description` кратко описывает одно изменение.
- `body` отделяется от заголовка пустой строкой и объясняет мотивацию, контекст и значимые последствия.
- Footer отделяется от body пустой строкой и оформляется как Git trailer.
- Для несовместимого изменения используй точный токен `BREAKING CHANGE: `, даже если остальной текст сообщения написан по-русски.

## Выбор type

Выбирай тип по намерению изменения, а не по расширению файла или количеству изменённых строк.

| Тип | Когда использовать | Не использовать вместо |
|---|---|---|
| `feat` | Новая наблюдаемая возможность | Любое добавление строк или файлов |
| `fix` | Исправление дефекта | Рефакторинг без исправления поведения |
| `docs` | Только документация | Документация вместе с изменением поведения |
| `style` | Форматирование без изменения поведения | CSS или UI-изменения, которые видит пользователь |
| `refactor` | Перестройка кода без новой функции и исправления дефекта | Замаскированная новая возможность |
| `perf` | Измеримое или целевое улучшение производительности | Обычный рефакторинг |
| `test` | Изменение только тестов | Тесты атомарной функции или исправления |
| `build` | Сборка, зависимости и packaging | CI-конфигурация |
| `ci` | CI/CD workflows и automation | Локальная сборка |
| `chore` | Техобслуживание, не подходящее под более точный тип | Универсальный тип по умолчанию |
| `revert` | Осознанный откат предыдущего коммита | Ручное исправление регрессии |

Сначала установи намерение, затем выбери самый точный тип. Не выбирай `chore` только из-за сомнения. Нестандартный тип допустим только тогда, когда он явно принят в локальных правилах проекта.

`feat` обычно соответствует `MINOR`, `fix` соответствует `PATCH`, а несовместимое изменение соответствует `MAJOR` в Semantic Versioning. Итоговое версионирование всё равно определяется release-политикой проекта.

## Выбор scope

1. Найди допустимые scopes в commitlint-конфигурации, документации и последних корректных коммитах.
2. Проверь, соответствует ли scope устойчивому модулю, пакету или предметной области.
3. Используй короткое имя в нижнем регистре, следуя локальному стилю.
4. Опусти scope, если изменение пересекает несколько областей или стабильное имя определить нельзя.
5. Не используй имя случайного файла или номер задачи как scope, если это не принято в проекте.

Не придумывай scope ради заполнения шаблона. Отсутствующий scope лучше ложной классификации.

## Стиль русскоязычного сообщения

- Пиши `description`, `body` и поясняющую часть footer по-русски, если проект не требует другой язык.
- Начинай `description` с глагола в инфинитиве: `добавить`, `исправить`, `обновить`, `ускорить`, `удалить`.
- Начинай описание со строчной буквы, кроме имён собственных и точных идентификаторов.
- Не ставь точку в конце заголовка.
- Стремись уместить заголовок в 72 символа. Это практическое соглашение, а не требование спецификации.
- В body объясняй причину и последствия, не дублируй заголовок и не пересказывай diff построчно.
- Сохраняй точные английские токены, идентификаторы, пути и названия API.
- Не добавляй emoji, имя автора, похвалу, служебные фразы Roo и выдуманные номера задач.

## Breaking changes и trailers

Для реального несовместимого изменения используй `!` в заголовке и подробно объясни миграцию в `BREAKING CHANGE` footer:

```text
feat(api)!: изменить формат ответа профиля

Ответ теперь содержит объект data вместо полей верхнего уровня.

BREAKING CHANGE: клиенты должны читать профиль из поля data
```

Не объявляй breaking change из-за внутреннего рефакторинга, который не ломает публичный контракт.

Другие trailers добавляй только на основании фактов и правил проекта:

```text
fix(auth): не обновлять истёкшую сессию

Closes: #184
```

Не выдумывай `Closes`, `Refs`, `Co-authored-by` и другие trailers. Если пользователь предоставил issue, выбери синтаксис согласно правилам хостинга и проекта.

## Примеры выбора сообщения

```text
Плохо: update files
Хорошо: feat(profile): добавить загрузку аватара

Плохо: chore: исправить падение авторизации
Хорошо: fix(auth): не создавать сессию без пользователя

Плохо: feat: добавить отчёт и исправить кеш и обновить README
Хорошо: разделить независимые намерения на несколько атомарных коммитов
```

## Фаза 1: Определи правила проекта

Сначала зафиксируй выбранный режим работы. Затем убедись, что находишься в Git-репозитории, зафиксируй исходное состояние и изучи недавний стиль сообщений:

```bash
git rev-parse --show-toplevel
git status --short --branch
git log -10 --format='%h %s'
```

Затем найди только применимые к затронутым путям источники правил:

- `AGENTS.md` в корне и во вложенных директориях;
- `CONTRIBUTING.md` и `README.md`;
- `.commitlintrc*`, `commitlint.config.*` и секцию `commitlint` в `package.json`;
- шаблоны PR и release-конфигурацию, если они прямо задают commit policy.

Применяй правила в таком порядке:

1. Явные инструкции пользователя в текущем запросе.
2. Локальные инструкции репозитория и commitlint.
3. Официальная спецификация Conventional Commits 1.0.0.
4. Значения по умолчанию из этого скилла.
5. История Git как свидетельство, только если явных правил нет.

Локальное соглашение может уточнить язык, scopes, длину заголовка и команды проверок, но не может отменить обязательную грамматику Conventional Commits.

## Фаза 2: Прочитай фактические изменения

До предложения сообщения выполни читающий анализ staged и unstaged изменений:

```bash
git status --short
git diff --stat
git diff
git diff --cached --stat
git diff --cached
git diff --check
```

- Анализируй staged и unstaged изменения раздельно.
- Обычный `git diff` не показывает содержимое untracked-файлов. Получи их имена из `git status --short`, затем безопасно прочитай только релевантные текстовые файлы.
- Не выводи целиком бинарные файлы, большие lock-файлы и сгенерированные артефакты. Для них исследуй метаданные и релевантную сводку.
- Если изменений нет, остановись. Не создавай пустой коммит.
- Если идёт merge, rebase или cherry-pick либо присутствуют конфликты, останови обычный процесс и точно сообщи состояние.
- Не трактуй уже staged файлы как своё разрешение на коммит. Это может быть подготовленная пользователем работа.

## Фаза 3: Проверь секреты и опасные файлы

Проверь имена файлов и содержимое diff на признаки:

- `.env`, приватных ключей, сертификатов и credential-файлов;
- API keys, access tokens, паролей и connection strings;
- дампов баз данных, персональных данных и случайных архивов;
- крупных или сгенерированных файлов, которые проект не ожидает хранить.

Если найден подозрительный секрет:

1. Не показывай полное значение в ответе.
2. Не добавляй файл в индекс.
3. Останови создание коммита.
4. Назови путь и категорию риска, замаскировав значение.
5. Предложи удалить секрет из изменений, обновить ignore-правила и при необходимости ротировать уже раскрытый ключ.

Не запускай команды проверки секретов, которые отправляют содержимое репозитория во внешний сервис, без отдельного согласования.

## Фаза 4: Сформируй атомарные группы

Одна группа считается атомарной, если она:

- выражает одно намерение;
- может быть независимо объяснена и отменена;
- включает необходимые тесты и документацию этого изменения;
- не смешивает независимые `feat`, `fix`, форматирование и инфраструктуру;
- не оставляет проект в заведомо сломанном промежуточном состоянии.

Не разделяй механически production-код и тесты его поведения. Разделяй независимые изменения, даже если они находятся в одном файле. Если нужен частичный staging, предложи `git add -p -- <path>`, но не запускай его без подтверждения и возможности пользователя контролировать hunks.

## Фаза 5: Покажи план и запроси подтверждение

До изменения индекса покажи точный план. Даже если пользователь уже написал "закоммить", этот план нужен как последняя безопасная точка контроля: человек видит состав, сообщение и проверки до изменения Git-состояния.

```markdown
## Предлагаемый план коммитов

### Коммит 1
- Намерение: <одно изменение>
- Файлы: <точный список>
- Проверки: <точные команды>
- Сообщение:

<полный header>

<опциональный body>

<опциональные footers>

### Исключено
- <файлы вне выбранного коммита и причина>

Подтверди коммит 1 или укажи изменения в составе и сообщении.
```

Для нескольких коммитов получай подтверждение каждого конкретного коммита. Не считай согласие с одним коммитом неограниченным разрешением на остальные.

Если пользователь просил только подготовить или проверить сообщение, остановись на этом этапе. В ответе явно напиши, что staging и commit не выполнялись.

## Запреты до подтверждения

До явного подтверждения запрещены любые команды, меняющие индекс, рабочее дерево, историю или remote, включая:

```text
git add
git reset
git restore
git checkout --
git commit
git commit --amend
git push
git clean
git stash
```

Список не исчерпывающий. Если не уверен, меняет ли команда состояние, сначала проверь документацию или не выполняй её.

## Фаза 6: Проверь подтверждение и актуальность плана

Подтверждение должно однозначно ссылаться на показанный коммит или полный план, например: `Подтверждаю коммит 1`.

Не считай подтверждением первоначальную просьбу закоммитить изменения, молчание пользователя, согласие с общей идеей или подтверждение плана, после которого diff изменился. Непосредственно перед staging повтори:

```bash
git status --short
```

Если состав изменений отличается от показанного плана, остановись, обнови анализ и получи новое подтверждение.

## Фаза 7: Добавь только подтверждённые изменения

1. Добавь только перечисленные пути: `git add -- <path...>`.
2. Для смешанного файла используй `git add -p -- <path>` только когда пользователь может контролировать выбор hunks.
3. Никогда не заменяй точный список на `git add .`, `git add -A` или `git commit -a`.
4. Не сбрасывай ранее staged изменения пользователя и не смешивай их с выбранной группой молча.
5. Проверь результат:

```bash
git diff --cached --stat
git diff --cached
git diff --cached --check
```

Сопоставь staged diff с подтверждённым намерением. Любое расхождение блокирует коммит до нового согласования.

## Фаза 8: Выполни свежие проверки

Проверки выполняются только для реального коммита. Для режима подготовки сообщения достаточно честно описать, что сообщение основано на прочитанном diff или предоставленном пользователем описании.

Выбирай проверки в таком порядке:

1. Единая команда проекта, например `npm run verify` или `make check`.
2. Таргетированные тесты затронутого модуля.
3. Релевантные линтер, typecheck и сборка.
4. Для документации: проверка ссылок, формата и установочного dry-run.

Покажи точные команды ещё в плане коммита. Не используй `--no-verify` для обхода hooks и не опирайся на старый вывод. Если проверка или hook падает, не создавай коммит: сохрани staged-состояние и сообщи точную причину. Если автоматических проверок нет, честно назови выполненную ручную проверку.

## Фаза 9: Создай коммит

Перед запуском ещё раз покажи точное сообщение. Для одного заголовка используй:

```bash
git commit -m 'docs(readme): уточнить установку скиллов'
```

Для body и footer передавай отдельные `-m`, чтобы Git сформировал пустые строки:

```bash
git commit -m 'feat(api)!: изменить формат ответа профиля' -m 'Ответ теперь содержит объект data вместо полей верхнего уровня.' -m 'BREAKING CHANGE: клиенты должны читать профиль из поля data'
```

В PowerShell и bash одинарные кавычки обычно безопасны для обычного текста. Если работаешь в другой оболочке, адаптируй только синтаксис кавычек, но не меняй подтверждённый текст сообщения.

Не подставляй секреты и непроверенные issue IDs. Не выполняй автоматический push.

## Фаза 10: Проверь результат и отчитайся

После успешного коммита выполни:

```bash
git show --stat --oneline --decorate --no-renames HEAD
git status --short
```

Сообщи короткий SHA, точный заголовок, реально прошедшие проверки и оставшиеся незакоммиченные изменения. Явно укажи, что push не выполнялся. Следующий коммит не создавай автоматически: повтори анализ и получи отдельное подтверждение.

## Специальные случаи

- **Revert:** запускай `git revert <sha>` только после отдельного подтверждения точного SHA. Не подменяй его ручным обратным изменением без причины.
- **Amend:** не предлагай по умолчанию. Применяй только по явному запросу после проверки публикации коммита и понимания пользователем переписывания истории.
- **Hooks:** не обходи отказ hook. Исправь причину или согласуй дальнейшее действие.
- **Конфликты:** не создавай обычный Conventional Commit поверх незавершённого merge, rebase, cherry-pick или конфликтов.
- **Staged изменения:** показывай отдельно и не сбрасывай без разрешения.
- **Generated files и lockfiles:** включай вместе с породившим их изменением, только если проект ожидает хранить их в Git.

## Красные флаги

Остановись и пересмотри план, если:

- тип выбран по имени файла, а не по намерению;
- `chore` используется как запасной ответ на сомнение;
- заголовок объединяет несколько независимых изменений;
- scope придуман и не подтверждается проектом;
- в staging попали файлы вне подтверждённой группы;
- проверки падают или предлагается `--no-verify`;
- обнаружен секрет, но процесс продолжается;
- первоначальная просьба ошибочно принята за финальное подтверждение;
- запрос был только на сообщение, но процесс перешёл к staging или commit;
- после коммита планируется автоматический push.

- [ ] Выбран режим работы: проверка сообщения, подготовка сообщения или создание коммита
- [ ] Прочитаны локальные правила и актуальный diff
- [ ] Нет подозрительных секретов и случайных файлов
- [ ] Коммит выражает одно намерение
- [ ] Type и scope подтверждаются фактическим изменением
- [ ] Breaking change обозначен и объяснён, если применимо
- [ ] Пользователь подтвердил актуальный состав и точное сообщение
- [ ] Staged diff совпадает с подтверждённым составом
- [ ] Свежие релевантные проверки прошли

Для режима проверки или подготовки сообщения последние три пункта не применяются: в отчёте явно напиши, что индекс и история Git не изменялись.

## Сценарии самопроверки

Перед публикацией изменений в скилле мысленно проверь его на сценариях:

1. Новая функция, независимая документация и форматирование разделяются по намерениям.
2. `.env` с тестовым токеном блокирует staging без вывода значения.
3. Изменение публичного API получает `!` и `BREAKING CHANGE` footer.
4. Production-код и тест его поведения остаются одной атомарной группой.
5. Просьба `закоммить всё` запускает анализ и запрос отдельного подтверждения.
6. Изменившийся после подтверждения diff аннулирует подтверждение.
7. Ошибка проверки или hook блокирует коммит без `--no-verify`.
8. Независимые остаточные изменения перечисляются, но не удаляются и не коммитятся.
9. Просьба "напиши сообщение коммита" завершается текстом сообщения, а не изменением Git-состояния.

Для проверки секрета используй только явно вымышленную фикстуру и удали её после прогона.
